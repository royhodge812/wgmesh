# Slice S-B spec — node agent + config writer

Status: **starter, ready for review.** No live testing yet — the R320 is
powered down (wiring relocated Nov 24) and no Go toolchain is on the
machine this was written on. See [Verify](#verify) for the checks to run
when power is back.

## 1. What S-B is

S-B puts a small agent on each mesh node. The agent does four things and
nothing else:

1. **Owns the node's keypair.** `wgmesh-agent init -name NAME` generates
   an X25519 keypair on the node and saves it to a state file
   (`wgmesh-agent.json`, mode 0600). The private key never leaves the
   node. Re-running `init` refuses to overwrite existing state, so a
   node's keypair — and therefore its mesh IP — is never silently
   replaced.
2. **Registers the node.** `wgmesh-agent register` takes a single-use
   pre-auth key (minted on the coordinator with
   `wgmesh admin create-key`), POSTs `{name, pubkey}` to the
   coordinator's `/register`, and saves the allocated mesh IP and peer
   list to state.
3. **Writes the WireGuard config.** After a successful register, the
   agent writes `wg0.conf` from the registration response. See
   [§3](#3-what-the-config-writer-writes).
4. **Brings the tunnel up or down.** `wgmesh-agent up` / `down` run
   `wg-quick up|down <config>`. `wgmesh-agent status` prints what the
   agent knows from its state file, without touching the network.

## 2. How it builds on Stage 1

Stage 1 (passed Nov 16, 2026, 20:55 CST) proved a real HTTP request
through the WireGuard tunnel returns HTTP 200. S-B changes nothing about
that tunnel or the coordinator:

- **Coordinator untouched.** S-B uses only the two S-A endpoints:
  `POST /preauth` (loopback-only, via `wgmesh admin create-key`) and
  `POST /register` (Bearer pre-auth key). No Slice A file is modified.
- **Allocator untouched.** Mesh IPs still come from `10.66.0.0/24`,
  lowest free from `.3` upward; `.1` stays reserved for the R320,
  `.2` for x390, `.255` broadcast. Re-registering the same pubkey
  returns the same IP, so an agent that re-registers after a rebuild
  keeps its address.
- **Listen port 51820.** The approved UDP port is the agent's
  `ListenPort`. Nothing else listens on it.
- **Registration transport is the tailnet, not the mesh.** A node
  registers *before* its tunnel exists, so it cannot reach the
  coordinator over the mesh yet. It reaches the coordinator over the
  existing Tailscale tailnet (live since Oct 20: x390, `muse`, phone;
  R320 joined Nov 24 as `pve`) or the LAN. The agent's `-server`
  flag defaults to `http://127.0.0.1:8080` (same default as S-A) and
  takes the coordinator's tailnet or LAN address when registering from
  another node. The mesh carries traffic only once the tunnel is up.
- **No endpoints yet.** S-A returns peers with an empty endpoint.
  Endpoints arrive with heartbeats (slice S-D). The config writer
  tolerates empty endpoints today and writes them when they appear.

## 3. What the config writer writes

`RenderConfig` (in `agent/config.go`) renders `wg0.conf` from the
interface settings and the peer list. Rules:

- `[Interface]`: the node's base64 private key, `Address = <mesh IP>/24`,
  `ListenPort = 51820`.
- **The node itself is excluded** from `[Peer]` sections. The
  coordinator returns every node including the caller; writing a peer
  entry for yourself would break the tunnel.
- **AllowedIPs is always the peer's mesh IP as a `/32`.**
- **Endpoint is written only when known.** Empty endpoints are omitted,
  never written blank.
- **Every peer gets `PersistentKeepalive = 25`**, so nodes behind
  NAT/CGNAT (the hotel link is CGNAT) keep the tunnel up.
- **Peers are sorted by mesh IP**, so re-renders are stable.
- The file is written atomically (temp file + rename) with mode 0600.

Example (fake keys):

```ini
# wgmesh node config — generated by wgmesh-agent. Do not edit by hand;
# re-run `wgmesh-agent write-config` (or register) to regenerate.
[Interface]
PrivateKey = <base64 private key>
Address = 10.66.0.3/24
ListenPort = 51820

[Peer]
# x390
PublicKey = <base64 public key>
AllowedIPs = 10.66.0.2/32
PersistentKeepalive = 25
```

## 4. Files

| Path | What it is |
| --- | --- |
| `agent/main.go` | CLI dispatch: `init`, `register`, `write-config`, `up`, `down`, `status`. |
| `agent/agent.go` | State file (0600, atomic write), keypair generation (stdlib `crypto/ecdh`, X25519), `/register` client, `init` / `register` / `write-config` commands. |
| `agent/config.go` | `RenderConfig`: the config writer, plus the `Peer` / `Interface` types (same JSON shape as S-A). |
| `agent/config_test.go` | Config writer tests: self-exclusion, `/32` AllowedIPs, endpoint omitted when empty / present when set, keepalive, sorting, bad-input rejection. |
| `agent/agent_test.go` | State round-trip and 0600 file modes for state and config. |
| `docs/slice-s-b-spec.md` | This spec. |

No new dependencies: the agent uses only the Go standard library, so
`go.mod` is unchanged. Build it with:

```bash
go build -o wgmesh-agent ./agent
```

## 5. Keys discipline (hard rule, same as S-A)

- Test with FAKE keys only. The tests generate deterministic fake keys
  from repeated bytes; they are not real keys.
- A real private key lives in exactly two places on the node: the agent
  state file and `wg0.conf`, both mode 0600. It is never printed,
  logged, committed, or pasted anywhere.
- Pre-auth keys are shown once at creation, passed by `-key` flag or
  the `WGMESH_PREAUTH_KEY` environment variable, and never logged.
  The agent never prints one.

## 6. What S-B does NOT do

- No heartbeat, no endpoint discovery, no `/peers` polling — slice S-D.
- No revoke — later slice.
- No daemon or auto re-register loop. The agent runs once per command;
  re-running `register` after another node joins refreshes the peer list.
- No UI, no changes to the coordinator, no changes to the live tunnel.

## 7. Review points for Roy

1. **ListenPort 51820** — matches the approved gate. Say so if it
   should be anything else.
2. **PersistentKeepalive 25 on every peer** — needed behind CGNAT.
   OK, or too chatty?
3. **State file location** — defaults to `wgmesh-agent.json` in the
   current directory. The R320 will want a fixed home for it
   (suggestion: `/etc/wgmesh/agent.json`, run as root). Confirm.
4. **`up` runs `wg-quick`** — needs `wireguard-tools` on the node.
   Confirm that is installed on x390 and the R320, or say which
   nodes need it.
5. **Self-exclusion** — the writer drops the node itself from
   `[Peer]`. Confirm that is the behaviour you expect (the
   alternative is trusting the coordinator to filter).
6. **Registration over the tailnet** — first registration happens
   before the mesh tunnel exists, so the node reaches the
   coordinator over Tailscale/LAN. Confirm the coordinator will be
   reachable that way from x390 and the R320 when you test.
7. **`write-config` does not refresh peers by itself** — it re-renders
   from saved state. A fresh peer list needs a re-`register` (same
   pubkey, same IP). Live peer updates come with S-D heartbeats.

### End-to-end run (R320 back on, coordinator running)

```bash
# On the coordinator host:
./wgmesh serve -listen 127.0.0.1:8080 -db wgmesh.db
KEY=$(./wgmesh admin create-key)

# On x390 (coordinator reachable over the tailnet/LAN — use its address):
./wgmesh-agent init -name x390 -server http://<coordinator>:8080
WGMESH_PREAUTH_KEY=$KEY ./wgmesh-agent register
cat wg0.conf        # check [Interface] and [Peer] sections (see .1/.2 note below)
./wgmesh-agent up
ping 10.66.0.1      # R320, once it registers
```

Note: `.2` is *reserved* for x390 in the allocator, but the allocator
hands out from `.3` upward and never assigns `.1` or `.2`. If x390
registers through the agent it will get `.3`, not `.2`. The reservation
means "don't give .2 to anyone else"; assigning x390 itself `.2` needs
either a coordinator-side reservation hook or a manual first
registration — that is a deliberate open question for review, not
something S-B silently works around. Same for the R320 and `.1`.

Expected results: `register` prints the mesh IP, `wg0.conf` contains
the `[Interface]` block and one `[Peer]` per other node, `wg-quick up`
succeeds, and `ping` between nodes answers. Two failed attempts at
the end-to-end run means stop, write it up, re-plan — do not keep
pushing (same rule as S-A).
